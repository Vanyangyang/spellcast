# Canvas 交付提示词自查

范围：用户截图中的反馈序号 73 通知。检查当前源代码、原生 MCP 定义和交付路径；未重新执行该历史反馈，未修改运行版。

以上范围描述对应首次自查。用户随后要求改流程，已完成实现与运行版更新；下面保留修改前的发现，实施结果见文末。

## 判断

交付机制有必要，当前提示词的组织不合适。应让用户实际提交的意图成为主语，将定位、读取、版本和回执要求作为必要的交付元数据；不能把优化理解为单纯删短。

## 发现

1. **用户正文没有出现在发给 Codex 的消息中。** `spellcast-bridge/src/feedback.rs:124` 的 `notice(event)` 只插入来源和序号；`desktop_delivery.rs:162` 将整段说明作为 `send_message_to_thread.prompt`。正文仍存在 `AgentEvent.text`，Agent 可通过 listen 读取，并未丢失，但聊天记录无法直接反映用户发了什么。截图中的英文内容是程序模板，并非用户撰写。
2. **所有请求套用同一套完整分支说明。** 普通文字留言也携带作品 bundle、旧回复引用、多位置锚点和 Canvas batch 的要求。真正需要这些分支时应由对应工具定义及读取结果提供，当前请求只携带相关约束。中文界面中固定出现整段英文协议，也不利于用户理解发送结果。
3. **用户意图与画布材料的优先关系不明确。** 模板强调如何更新、关联结果和 ack，却未明确“测试、解释、继续讨论”不等同于授权修改内容或执行候选方案。这是误解风险，尚未通过本次审查复现为实际误执行。用户留言应决定任务，选项及引用材料只提供上下文；必要的返回画布也不应强制改写原内容。
4. **防重复要求可以更精确。** `lib.rs:223` 的事件流可能包含已确认历史事件；`mcp.rs:579` 另行返回 `pending_sequences`。当前模板只说检查 pending，没有指出应使用该明确字段。应以目标序号仍在 `pending_sequences` 中为处理前提，不能以出现在 `events` 中作为依据。

## 应保留的约束

- 精确的来源与反馈序号、原任务身份及工作区核验。
- 修改前读取相关内容；区分提交时引用版本与当前版本，保护发送后发生的用户编辑。
- 实际回写与反馈序号关联；完成后才确认，重复通知不重复执行。
- 原生工具缺失时如实说明。HTTP 测试不能冒充宿主集成成功。

这些要求已有部分代码支撑：任务目标在提交前核验；反馈结果验证来源；请求 ID 提供重试保护；MCP 提供待处理序号和回执。提示词仍需说明意图和操作顺序，但无需为每条留言重复整份接口手册。

## 建议形态

可见消息首先展示“来自 Spellcast Canvas”、用户原文、相关内容名称；来源和反馈编号置于清晰的元数据区域。保持实际留言与引用材料分开，避免将画布内容中的文字当作额外授权。

交付指引只要求：先读取并核对该条未处理请求，按用户原意处理；需要继续内容时回到原对象；使用实际读取版本保护编辑；关联结果并确认。作品、组合和多位置读取要求随对应请求按需提供，通用 API 参数放在原生工具契约中。

当前通道只有可见的 `prompt` 字符串；不能声称已存在可隐藏协议的专用消息通道。

## 后续改动应验证

- 普通留言在 Codex 中保留用户原文和正确目标；不让元数据遮蔽正文。
- “这只是测试”不触发内容修改或候选方案执行；解释性请求遵循其范围。
- 多次本地选择和编辑仍为零投递，显式发送仅创建一次请求并携带最终版本。
- 已确认通知不重复执行；发送后内容又被修改时不覆盖新编辑。
- 作品或多锚点请求读取完整依赖，失败不被标记为已完成。

证据等级：代码与接口审查。此轮未运行新的模型行为验收，未宣称上述风险已实际发生。

## 后续已实施

通知改为原文和内容标题优先；复杂处理要求随精确请求的工具结果按需返回。新增按 `source_id + sequence` 只读该条未处理反馈的路径，返回待处理状态、上下文处理指引和已有回写记录。已确认事件不再从此路径返回；测试、询问与执行范围由用户留言决定，不为产生回执而强行修改画布。
