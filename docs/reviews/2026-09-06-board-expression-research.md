**Spellcast 板模式：AI 表达形式与开源方案｜2026-09-06**

结论：把板建设成 **Agent 可以组织、更新，用户可以选择、修改和继续推演的回复载体**。第一版优先做混合回复、方案对照、有语义的关系图和体验分镜。借鉴 json-render / A2UI 的结构化表达方式，关系图重点验证 X6；其他渲染器按真实内容需要接入。

**本次用户明确的产品流程**

气泡被采纳 → 内容进入板 → 用户进入板模式 → Agent 使用板提供的形式呈现回复 → 用户在这些内容上继续反馈和创作。

这修正了前一份审查的侧重：气泡阶段需要旁念克制；主动进入板模式后，完整回复可以由板来承载。不能把“气泡不得承载主回复”扩展成“板也只能放旁念”。板不是只接收收藏的终点。

建议把“采纳入板”和“打开板模式”分开：采纳先留下内容，用户进入板后再展开回复，避免收藏动作突然抢走前台。这个切换细节属于建议，尚未替用户确定。

**现有实现为什么还不够**

当前几种形式主要是在重新排列同一类文字碎片：

- [shared.ts](G:/VibeProj/spellcast/src/forms/shared.ts:12) 把卡片渲染为类型、标题和一个正文段落，缺少丰富的内容块。
- [layout.rs](G:/VibeProj/spellcast/spellcast-core/src/layout.rs:38) 创建碎片时把标题截到 22 字、正文截到 140 字。板要承载完整回复，应保存全文，在界面上折叠或渐进展开，不能在数据层丢掉内容。
- [timeline.ts](G:/VibeProj/spellcast/src/forms/timeline.ts:11) 用 x、z 坐标排序，没有明确的步骤序号或时间含义；移动位置不应该改变叙事顺序。
- [stack.ts](G:/VibeProj/spellcast/src/forms/stack.ts:6) 按“观点、想法、问题、风险、行动”分列，尚不是“多个方案 × 相同评价维度”的对照。
- [constellation.ts](G:/VibeProj/spellcast/src/forms/constellation.ts:25) 可以画连线，但表达模型主要是父子关系，难以区分“导致、依赖、支持、反对、备选”。
- 当前 [present](G:/VibeProj/spellcast/spellcast-core/src/session.rs:119) 会改变整板的 form；后续回复可能改变用户正在阅读的整体组织方式。需要允许一块回复内部选择表达形式，而不是每轮都重排整板。

所以这次的提升应先改变“内容能表达什么、如何连续修改”，再优化外观。

**最适合先做的表达形式**

| 形式 | AI 用它回答什么 | 用户可以怎样继续 | 实现建议 |
| --- | --- | --- | --- |
| 混合回复 | 解释一个想法：短文、关键图、依据、待决定点组合在一起 | 只展开相关细节，在具体段落或图上追问 | 作为默认形式；先做一小组稳定内容块，用现有 DOM/CSS 呈现 |
| 方案对照 | A/B/C 的不同机制、收益、代价和适用条件 | 选择方向、改约束、沿选中方案继续 | 同一组评价维度对齐；不填没有依据的分数；先用原生布局 |
| 关系与机制图 | 因果、依赖、状态转换、分支剧情、系统结构 | 点选节点/边，修改关系，展开一个局部 | X6 作为重点候选；AI 提交实体和有标签的关系，布局交给渲染器 |
| 分镜与步骤 | 玩家旅程、叙事节拍、动画、交互流程 | 调整顺序、拆分一拍、修改动作或反馈 | 独立 sequence 字段；画面、动作、感知与设计目的分开；首版可用原生布局 |
| 树状发散 | 层级明确的灵感、分类、章节和探索方向 | 折叠分支、选一支继续展开 | Markmap 适合文字到导图；需要完整语义编辑时回到结构化数据 |
| 数据与交互推演 | 数值趋势、方案变量、调整参数后发生什么 | 改参数、检查结果与假设 | 有真实数据或明确示例规则后再接 ECharts；计算行为预先定义，避免生成任意执行代码 |

媒体、参考图与局部标注也很适合创作，但需要先准备真实素材和来源。它们应能放进混合回复或分镜，不必另造一整套使用模式。已有 Three.js 保留给空间本身有意义的内容；文字和取舍默认用清楚的二维排版。

正式产品中由 Agent 按任务选择合适形式，用户需要时可切换或要求重组。本次样稿把形式选择直接摆出来，是为了比较设计，不意味着正式界面每次都要用户先选模板。

**GitHub 与官方资料筛选**

以下许可证按本次官方仓库及 GitHub 元数据核对；选用意见是针对 Spellcast 当前 Tauri + 原生 TypeScript 前端的判断，尚未做依赖体积、性能或原生 WebView 集成基准测试。

| 项目 | 已确认的能力与许可证 | 对 Spellcast 的判断 |
| --- | --- | --- |
| [json-render](https://github.com/vercel-labs/json-render) | Apache-2.0；组件目录、schema、动作、增量规格流；提供多种框架渲染器 | 最值得借鉴的 AI 表达组织方式。先评估 core 的目录与校验部分；不能把 React/Vue 等完整示例当成当前原生 TS 项目的即插即用实现 |
| [A2UI](https://github.com/a2ui-project/a2ui) | Apache-2.0；带 ID 的声明式组件、数据模型与局部更新，客户端使用自己的组件实现 | 学习跨宿主表达契约、局部更新与用户动作回传。它和 MCP 所处的层不同，不必替换现有 MCP，也不必第一版完整实现整个协议 |
| [AntV X6](https://github.com/antvis/X6) | MIT；基于 SVG/HTML 的图编辑，自定义节点、事件及多种编辑扩展 | 关系图的首个集成候选，可用现有 TS 技术路线验证。它提供编辑引擎，业务关系语义仍由 Spellcast 定义 |
| [Mermaid](https://github.com/mermaid-js/mermaid) | MIT；由文本定义生成流程、时序等图 | 快速说明和导出很合适。文本生成图不等于可无损拖动编辑；首版可作为一种图块，不能直接充当整个板的数据模型 |
| [Markmap](https://github.com/markmap/markmap) | MIT；Markdown 转思维导图，提供官方交互示例 | 适合层级发散和折叠阅读。它不能覆盖任意关系、对照、分镜或富媒体回复 |
| [Excalidraw](https://github.com/excalidraw/excalidraw) | MIT；可嵌入的自由画板，官方集成需要 React/ReactDOM | 适合之后验证手绘表达、自由摆放与批注。现阶段若整体替换板，会同时引入框架与编辑器集成工作，先作为特定画板区域的候选 |
| [Apache ECharts](https://github.com/apache/echarts) | Apache-2.0；交互图表与数据可视化 | 作为按需图表组件；先确认真实数据任务，不提前把产品做成数据仪表盘 |
| [tldraw](https://tldraw.dev/community/license) | 当前为 tldraw 自有许可；生产使用需要试用、商业或 hobby 等适用许可 | 借鉴画布交互质量，不把它当作无额外许可条件的开源基础依赖 |

json-render 的 [Catalog 文档](https://json-render.dev/docs/catalog) 将可用组件和可用动作作为模型表达的词汇表。对 Spellcast 很有价值的一点是：让 AI 选择“对照、步骤、关系、证据”等表达手段，排版、尺寸和交互细节由产品统一完成。无需让每次回复都重新生成一套界面代码。

A2UI 的 [数据流说明](https://a2ui.org/concepts/data-flow/) 展示了 Agent 到界面的更新以及用户动作回传。可借鉴其稳定 ID 与局部更新思路，避免修改一个节点就替换整张板。其当前仓库说明 v0.9.1 是 v0.9 协议族的生产发布，v1.0 仍为候选规范；接入时应固定版本，而非从搜索摘要里的旧版本信息推断。

Excalidraw 有 [Mermaid 转换工具](https://docs.excalidraw.com/docs/@excalidraw/mermaid-to-excalidraw/api)，但官方文档明确：目前流程图可转为可编辑元素，其他图种会作为图像呈现。不能宣传成“所有 AI 生成的 Mermaid 图都能无损编辑”。其 [安装说明](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/installation) 也确认了 React 依赖。

**我建议采用的产品结构**

一张板可以容纳多块回复或创作区域。每块保留来源气泡、原任务、用户选择和更新版本，允许文字、关系图、对照与分镜共存。形式属于内容区域，不必是整张板唯一的模式。

Agent 提交的应是表达意图与结构：对象、关系、步骤、比较维度、内容、可选动作。位置、连线路径、换行、缩放和视觉风格由 Spellcast 决定；用户调整过的位置与文字优先保留。模型无需每次计算像素坐标，也不能把用户改写后的版本无声覆盖。

先定义少量稳定能力即可：文字说明、选项/对照、步骤/分镜、关系图、媒体引用，以及“选择这一项、展开此处、补充约束、添加旁注”这些动作。使用稳定 ID 局部更新，校验失败时保留上一个完整版本并退回可读文本。现有 MCP 继续负责投递与读反馈，现有 SQLite 继续负责保存；没有必要同时引入新的模型宿主或消息平台。

用户在板上的操作需要区分两类：纯视图操作，例如平移、缩放，不触发模型；有表达意图的操作，例如改字、改关系、选方案、发起局部追问，作为带目标位置的输入交回对应 Agent。板模式开启也不意味着主任务的短命 Observer 自动变成长期聊天者，回复责任仍需明确绑定原任务或用户指定的处理者。

“板上的完整回复”同样允许诚实表达不确定性：证据、推测、待验证方案分别标清；未知数据留空；来源可以展开查看。丰富的呈现不能把未经验证的内容包装成事实。

**精致好用的验收应落在这些细节**

- 采纳后只产生一份内容，来源可追溯；重复点击不会造出副本。
- 第一屏能读出这次回复的核心与下一步选择，复杂细节按需展开。
- 选定一个方案后，切换表达形式仍围绕同一内容；旁注不会跟到另一个方案。
- 表达切换保留语义。例如分镜顺序由 sequence 决定，不跟卡片位置一起漂移。
- AI 增量更新只改变相关区域，正在编辑的文字、用户布局和阅读位置不跳动。
- 新增、改写、连线与排序可以撤销；删除和撤销撤回的是明确对象。
- 关系图有可读的边含义，文字不与连线重叠；复杂图可以聚焦局部。
- 中英文长文本、深浅主题与不同窗口宽度可读；完整内容不因卡片尺寸永久截断。
- 明确的用户输入送给对应任务；无法立即处理时显示待处理，而不是假装已经理解。
