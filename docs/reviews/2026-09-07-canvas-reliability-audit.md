# Canvas 主线可靠性检查 · 2026-09-07

结论：Canvas 已有真实的结构化内容与持久化底座，但还不能把“用户在画布上发起要求，原 Agent 可靠接手并更新结果”作为已完成的产品承诺。当前表达能力足以验证主线，建议暂停新增表达形态，先补任务接续、编辑保护和连续使用验收。

这是一次检查与优先级建议，没有实现新功能，也没有推送。Canvas / 画布是已确认的名称；GitHub 介绍、README 与 Skill 的命名同步仍按用户要求留到下次推送。

旧的板表达研究记录描述过“只有短卡片和样稿”，那是当时状态，已不适合作为今天的完整实现结论。当前未跟踪的 `src/board-replies.ts` 与 `.css` 也不是正式渲染入口；本轮保留它们，没有擅自清理。

## 优先补的缺口

### P1：画布输入保存后，没有可靠的原任务接续

`src/main.ts:754-780` 的提交路径调用 `say` 并显示等待原任务；`spellcast-bridge/src/lib.rs:557-579` 只等待已有 listen 调用，`658-684` 的通知也只是唤醒正在等待的工具调用。`spellcast-bridge/src/mcp.rs:36` 明确不唤醒安静或关闭的模型。

因此，持久反馈是已实现的，但“继续”不等于原 Agent 已收到、正在执行或已经完成。空闲但不监听的任务同样可能不处理，不能只把问题归为关闭了 CLI。

最小下一步：先针对已经有实际验证基础的 Codex 宿主，补明确的 source_id → 实际任务绑定和投递。沿用持久反馈与 ack，不另造第二份请求记录。分别表示待接手、已投递、失败/投递未知与已处理；结果回到原 reply/block。不能根据最近会话或模型标签猜测接收者，也不能投递不明就自动再发一次。

`docs/reviews/2026-09-06-codex-board-feedback.md` 仅证明当时打开的 CLI 能接收 queue，明确未接入按钮；它不证明关闭宿主后的恢复。宿主接口的具体选择需要实施时再验证当前环境，本检查不将旧 CLI 证据当作通用兼容保证。

### P1：结构变化可能移除未保存草稿

普通同类型内容更新保留编辑器，保存失败也保留草稿；这是已有保护。问题出现在结构变化：

- `src/replies.ts:2173-2176`：同 ID 的内容块类型改变，直接销毁旧 view。
- `src/replies.ts:2186-2189`：内容块从回复消失，直接销毁旧 view。
- `src/replies.ts:584-585`：销毁会移除包含编辑器的 DOM；这些分支没有检查未保存输入或提供恢复入口。

触发例：用户正在编辑某段文字或写局部追问，Agent 用新 ID 重组该段，或把它换成另一种类型。旧编辑器被移除，草稿不再可用。数据库版本检查保护的是已保存状态，不能保护尚未提交的输入。

这是静态代码路径确认的风险，本轮未用真实桌面操作复现。最小修复应保留受影响草稿并提示结构已变，再由用户复制/合并/舍弃；暂不引入通用协同编辑或完整版本历史系统。

### P2：连续工作验收仍不足

构建、后端测试、气泡录屏、四种形态演示各自有价值，但不能替代一次无人工中转的“采纳 → 展开 → 修改约束 → 原任务更新同一区域”。

先用一个真实项目验收以下行为，不规定气泡数量或为了录屏制造内容：

1. 采纳一条真实旁念，发起展开，正确的原任务给出一块可继续工作的回复。
2. 选择一个方案并补约束，结果更新同一回复，保留无关内容、用户选择、编辑草稿与阅读位置。
3. 原任务空闲、忙碌、不在线时均显示真实状态；绑定丢失不误投另一任务。
4. 重复点击、传输结果不明、应用重启后，既不丢请求，也不悄悄重复执行。
5. 用户编辑期间遇到同块更新、删块、换类型与保存失败，输入始终可找回。

## 先不加什么

不新增白板模式、图表库、自由绘图、媒体系统、多宿主统一调度或新的 Agent 平台。现有四种内容块已经能承载主线；只有真实任务明确卡在表达能力上，再添加对应的一种能力。

这里的技术质量应体现在：来源绑定准确、请求可恢复、局部更新不破坏用户输入、状态可解释、真实使用过程流畅。性能问题应先测量再优化，不在本轮根据依赖体积或状态存储结构猜测卡顿。

## 追加复核：愿景、选型、Canvas 名称与 Codex 及时反馈

### 愿景兑现情况

最早明确的目标是：气泡被采纳进入板，进入板模式后，Agent 使用板提供的形式回复，用户可以沿着这些内容继续反馈和创作。按这个目标，结论是**部分兑现，尚未完成**。

- 已兑现的基础：任务相关的旁念、采纳、完整结构化回复、局部选择/编辑/追问、持久反馈与版本保护。
- 尚未兑现的关键体验：用户留在 Canvas 中，就能让正确的原 Agent 连续接手并更新同一内容，无须另一个操作者转发指令。
- 命名讨论中关于自由摆放、关系创作、参考图等场景属于方向想象，不能当作已经实现的功能，也不应把全部想象自动升级成本轮必须完成的范围。

前阶段验收过分强调了“能显示几种形态”，对“能持续完成实际工作”的验收不足。应提高完成标准，不能用最小实现或测试数量替代完整用户路径。

### 技术选型判断

| 选择 | 判断 | 当前不足来自哪里 |
| --- | --- | --- |
| Tauri + Rust + 本地 SQLite | 与桌面浮窗、系统集成、本地持久状态的职责匹配，当前无证据要求重选 | 主线接续和恢复没有因选用这些组件而自动完成；跨平台表现仍须各平台实测 |
| 原生 TypeScript/DOM + 类型化内容块 | 四种内容块使用这条路线合理；可读文档不需要全部变成图形对象 | 用户草稿、结构更新、动作回传需要完整编辑语义和验证；手写渲染器必须承担这些职责 |
| AntV X6 | 适合关系图编辑区域，选库方向成立 | 当前只使用节点移动、选择、缩放等能力，连线编辑被主动关闭；尚未形成完整关系编辑流程 |
| Three.js | 目前用于碎片的空间展示，是可选表现能力 | 不能证明 Canvas 的协作价值，继续打磨 3D 不会补上任务接续 |
| MCP + Skill + listen/ack | 已提供模型输出、反馈读取和确认接口 | 当前交付没有宿主任务调度与活跃状态回传；只靠 Agent 自行 listen，无法承诺及时响应 |

Tauri 的官方架构将窗口、全局状态与数据库连接放在 Core，WebView 负责界面；这支持上述分工判断，也明确要求考虑平台差异。[Tauri 进程模型](https://tauri.app/concept/process-model/)

X6 官方定位本就是图编辑引擎，并提供交互控制与撤销重做能力。当前能力窄不等于库本身只能做到这些；是否接入撤销，还需与 Spellcast 的持久状态和 Agent 更新保持一致。[X6 简介](https://x6.antv.antgroup.com/en/tutorial/about)、[交互配置](https://x6.antv.antgroup.com/en/api/model/interaction)、[撤销重做](https://x6.antv.antgroup.com/tutorial/plugins/history)

因此，对“是不是得过且过”的直接回答是：**基础选型没有明显敷衍，但此前把组件可用当作产品闭环接近完成，验收标准偏低。** 当前优先补集成和编辑语义；没有足够证据支持为了换框架而重写。没有直接安装 A2UI/json-render，也不能单独作为好坏依据；应检验稳定 ID、结构校验、局部更新、用户动作和恢复是否真正成立。

### Canvas 是否名副其实

**现在是可编辑 AI 回复工作面的早期形态，还不是完整的自由共创画布。** 名称可以保留，成熟度描述应收紧。

具体证据：

- `src/replies.css:259-310`：完整回复是滚动文档、居中的 panel、纵向 grid 内容块；`src/replies.ts:2114` 使用回复标签导航。
- `src/board-workspace.css:1-13`：完整回复与自由碎片共用窗口，但仍是切换的两套视图，回复视图隐藏碎片布局和新增碎片按钮。
- `src/reply-types.ts:64-74`：完整回复没有顶层空间位置、区域或跨回复关系字段；图内坐标只属于 graph block。
- `src/replies.ts:1515-1529`：图支持平移、缩放、节点移动，禁止连接节点、修改边和端点；图中的关系当前主要由 Agent 提交。

这不要求下一版立刻做成无限白板。更贴近原愿景的标准是：用户能在内容对象上表达有效意图，组织或修改所需结构，Agent 根据这些意图继续更新，用户工作不被破坏。若这些仍不成立，仅改名 Canvas 和添加更多布局不足以兑现愿景。

### 与 Codex 的“及时反馈”是否验证

**没有验证完整的及时双向反馈链路。** 现有证据必须拆开看：

| 已有证据 | 可以证明 | 不能证明 |
| --- | --- | --- |
| 真实 Codex CLI 调用原生 Spellcast MCP，后来也有独立子代理完成观察协议 | 对应测试任务在对应时刻能调用工具并向桌面提交内容 | 每次启动都连接正常、每条画布输入都触发回复 |
| 2026-09-06 外部执行 `codex queue` 后，同一个 CLI 收到指令并继续验证日历 | 当时打开的 CLI 能接受外部接续；本轮任务记录回读也确认日历复验和原生 bubble 调用 | Canvas 按钮已接入该路径，或者 CLI/宿主关闭后能可靠恢复 |
| source-scoped listen/ack 与重启持久测试通过 | 请求能保存、按来源读取与确认 | 正确的 Agent 会及时开始处理，或者多久更新到画布 |

本轮回读的旧 CLI 记录还包含一次后来的只读预检返回 `NOT_CALLABLE`。这不能抹去之前的成功，但说明不能把某次成功扩大为连接始终有效。桌面任务读取器给出的 `notLoaded` 也只描述其所见运行时，不能据此判断另一个 CLI 实例是否在线。

目前没有“画布点击 → 对应任务接收 → 开始处理 → 原回复首个可读更新 → 处理确认”在同一事件上的完整时间线。单次 MCP 几毫秒的工具耗时、外部 queue 成功，均不能当作端到端响应时延。

Codex 官方 App Server 已有 `thread/resume`、`turn/start`、带 `expectedTurnId` 的 `turn/steer` 及进度通知。这提供了应调查的正式集成接口；实际能否连接并控制用户正在使用的那个运行时，仍须现场验证，不能直接对另一实例启动同一任务。[Codex App Server](https://developers.openai.com/codex/app-server)

下一轮接续验收应同时记录上述时间点，分别测试空闲、忙碌、离线、重启和重复输入。先得到真实延迟与失败分布，再确定响应目标；本检查不编造延迟承诺。上一轮的 54 项通过、1 项忽略仍是组件/库级验证，本轮仅补证据与评估，未修改实现或重复运行相同测试。
