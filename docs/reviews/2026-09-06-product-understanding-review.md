**Spellcast 产品理解与闭环审查｜2026-09-06**

审查对象：[修复 MCP 预览与其他客户端配置](codex://threads/01a0604e-db1d-7210-adb1-5708c5c1270e)。

**后续用户澄清：** 气泡被采纳后进入板，进入板模式后 Agent 可以用板提供的方式呈现回复。本报告主要审查了气泡与反馈链路；其中“主回复与旁念分开”的限制不应扩展为“主动板模式也只能放旁念”。板作为完整回复与创作载体的补充审查、开源选型和交互样稿见 [板模式表达研究](G:/VibeProj/spellcast/docs/reviews/2026-09-06-board-expression-research.md)。

我的判断：**之前模型后来已经能准确复述产品理念，但没有持续用这个理念决定开发顺序、实现边界和验收方式。最大的不足，是把“让有价值的旁念在创作过程中自然出现”推进成了配置、窗口、板和工具的集合。** 这些基础设施有价值；核心使用闭环仍缺证据。最后提出的 Observer 方向值得验证，但“改一下 Skill 就能完成注意力分离”的结论过早。

以下方案是本次审查建议，未替你更改产品方向，也未实施代码改造。

你已明确表达的产品意图是：LLM 在主对话中仍然有用，不把对话带偏，同时能在电脑上表达质疑、建议、提醒、记忆和旁念；服务于开发者的想象性创作；存在于用户真实桌面，不依附某个 IDE、CLI 或模型。原对话中你重新给出了英文设计理念；另一个任务中的“用户真实的桌面，所以 Spellcast 无需单独搞个桌面”也已核对到原文。

由此推导出的核心体验应是：**我继续做原任务；一个有独立价值的想法轻轻出现；我可以忽略、留下或回应；回应有人接手，值得记住的内容以后能在合适时刻找回来。** “独立”主要是展示位置和使用连续性，不意味着 Spellcast 必须自己托管模型。

**1. 对产品纠偏的回应停在换词，缺少行为交付。优先级 P0。**

证据很直接：你说“agent 的桌面这个说法不对”后，模型改成了“你的旁念桌面”；你重述原始理念后，它又改成“对话之外的舞台”。随后你说“现在就开工”，该轮交付是 README、三语文案和演示板定位；你追问“实质的内容呢？怎么做的？”，模型自己承认没有新增产品行为。

问题不在于文案不能改，而在于它没有从你的纠偏继续追到：主任务进行时，哪条新行为会让用户感受到产品？当前 [README](G:/VibeProj/spellcast/README.md:5) 已清楚列出冒泡、收藏、板，实际桌面小窗也已存在，不能把产品说成全是空壳。但这还没有回答旁念如何自然产生。

解决方案：下一次开发只围绕一条可观察的用户旅程交付，例如“真实创作任务中产生一条有用的旁念，用户回复后由正确任务继续处理”。每轮交付说明四件事：用户现在能做什么、由哪条实际链路完成、哪些步骤真实验证了、哪些仍然未知。文案一致性作为随行为更新的附属工作。

验收：用户无需输入“抛个测试泡”，也无需盯着连接页；完成一次真实任务中的产生、看到、回应、接手。单次成功只能证明链路，不足以证明旁念长期有用。

**2. 缺少可靠的启动入口；“默认安静”可能落成“需要用户反复提醒才会使用”。优先级 P0。**

当前 [产品 Skill](G:/VibeProj/spellcast/skills/spellcast/SKILL.md:3) 主要在提到 Spellcast、气泡或调用工具时加载，并明确不因创意任务本身而加载；正文要求默认不冒泡。这些限制有助于克制，但没有构成一套会话启用和事件触发机制。现有 MCP 指令也只描述什么时候可以调用，不能证明调用会自然发生。

解决方案：先为一个宿主验证会话级启用方式。用户启用后，宿主在有新信息的自然节点提供一次简短上下文；没有新信息就不触发。输入应包括创作目标、已知约束、正在讨论的取舍，以及最近相关反馈。无需把全部历史复制给观察者，也无需每一步操作都触发。

不要只输入 diff、测试和错误摘要，否则它很容易变成第二个代码审查员。这里应允许有根据的异议、另类解法和联想。例如主任务继续设计战斗技能，旁念提出“把施法失败做成角色犹豫动作，会不会更贴近这个角色的性格？”这属于创意候选；真正阻塞主任务的错误仍应直接交给主 Agent。

验收：普通例行操作能保持安静；明显重复的上下文不再次触发；有价值的非阻塞联想能出现。评价是否具体、有用、独立于正文，不能用“冒泡数量”代替产品价值。

**3. Observer 是合理的执行方向，但最后一轮没有解决它的生命周期。优先级 P0。**

模型正确看到了“展示分开”和“思考并行”是两件事。但它同时提出“短命子任务安静结束”和“用户回复后在下一个检查点读取”，没有指定子任务结束后谁保存上下文、谁接手反馈。主 Agent 整理快照、启动子任务、接收完成消息仍有成本，不能保证零影响。本次所读最后一轮没有实际子任务调用，也没有实现改动。

建议分清两个责任：临时 Observer 负责生成和筛选候选；宿主适配负责来源、调度、反馈游标和原任务恢复。先复用宿主已经提供的子任务能力。是否能直接访问 Spellcast 工具、是否会自动把结果回灌主对话、主任务结束后还能否运行，必须逐项实测，不能由 Skill 的文字承诺代替。

本次当前宿主可调用工具目录中没有发现 `spellcast_*`。这只证明本任务尚不具备原生调用的可见证据，不证明应用离线。接入试验的第一步应是确认当前宿主与其子任务实际获得了工具，再做真实投递。REST 测试可以诊断后端，不能作为原生宿主接入验收。

验收：主 Agent 不等待 Observer 的旁念结果；记录主任务是否被暂停及增加的耗时、token；Observer 无候选时安静完成；主任务已经结束时，用户仍看得到反馈待处理状态，且之后可以恢复处理。暂不支持宿主唤醒时，明确等下次恢复处理，不承诺即时应答。

**4. 反馈能读到，但还不是可靠的多任务收件箱。优先级 P0。**

当前 [AgentEvent](G:/VibeProj/spellcast/spellcast-core/src/inbox.rs:8) 只有序号、时间、类型、气泡/碎片编号和文字，没有所属客户端会话、原任务或接收者。[listen](G:/VibeProj/spellcast/spellcast-bridge/src/lib.rs:310) 按全局 `since` 返回事件；[Inbox](G:/VibeProj/spellcast/spellcast-core/src/inbox.rs:29) 最多保留 256 条。SQLite 保存的是状态快照，无法恢复已经从该队列淘汰的旧事件。

因此：两个任务都可能读到同一反馈，却不知道是否该处理；长时间未读取的明确回复可能被后续事件挤出。多个客户端能握手，并不等于回复能准确送回原任务。这是基于结构和读取路径推导出的风险，本次没有制造串台或丢消息的运行事故。

解决方案：气泡、碎片和回复记录来源标识，至少能定位宿主、原任务和一次候选；明确回复形成持久待处理项，记录处理确认。沿用现有 SQLite，已处理历史可以有限保留，未处理的用户回复不能随诊断事件一起淘汰。读取游标和候选上下文归宿主适配持有，不放在短命 Observer 的临时记忆里。交付可重试，按事件 ID 避免重复执行，别承诺网络层“恰好一次”。

前端只需让用户理解“已收到，等待原任务处理 / 已处理 / 暂时无法送达”；技术 ID 不必暴露。对于无归属的板上留言，保留为待分配输入，不让碰巧轮询到的 Agent 自动认领。共享桌面仍然可以统一呈现，不必为每个任务另造一套桌面。

验收：Codex 的两个不同任务，以及 Codex 与另一个客户端同时使用时，回复送回正确任务；Observer 退出后仍可接手；重启后未处理回复仍在；超过 256 条其他事件不丢明确回复；重试不重复触发任务动作。

**5. “不打断”主要靠提示词，执行层的注意力控制不足。优先级 P0。**

已有保护应保留：气泡创建使用 [focused(false)](G:/VibeProj/spellcast/src-tauri/src/desktop.rs:221)；`present` 单次最多解析 3 个气泡，且板处于 focus 模式时不解析其气泡。可是独立 `bubble` 仍直接投递，单次上限不构成跨调用、跨 Agent 的总量控制。此外，[present(open=true)](G:/VibeProj/spellcast/spellcast-bridge/src/lib.rs:243) 会请求 [show/set_focus](G:/VibeProj/spellcast/src-tauri/src/lib.rs:68)。

解决方案：在共享投递入口统一处理用户暂停、当前显示数量、短时重复和过期候选；所有投递路径遵循同一策略。初始并发显示数量可以从 1 个开始试用，但它是待验证的产品参数，不是全局 Agent 规则。明确用户请求的演示与自主旁念应能区分。自主旁念不能自行把板抢到前台；展开应由用户输入驱动。

触发频率和投递频率分开控制：先避免无意义地启动 Observer，再避免多个合法候选同时占据桌面。被拒绝的候选返回明确状态，不能立即换句话重投。

验收：持续键盘输入时不丢焦点；多个 Agent 同时提交时也不出现气泡洪水；暂停后所有自主投递路径都停止显示；重复候选不重投；用户主动展开仍正常工作。实际桌面输入和显示器验证不可用 HTTP 检查替代。

**6. “已抛出”目前不足以证明窗口成功，更不足以证明用户看到。优先级 P0。**

对话中有过“服务 HTTP 200，所以桌面窗口和热更新均在运行”的汇报，紧接着你问“在哪”。后来模型又承认找不到可定位的窗口。其后关于 Vite 冷启动的解释，现有对话检查点也不足以单独证明完整因果和视觉恢复；应保留为当时的排障判断，而不是产品可靠性结论。

更直接的当前代码问题在 [Desktop::throw](G:/VibeProj/spellcast/src-tauri/src/lib.rs:24)：安排主线程创建窗口后就增加数量并返回；真正创建失败只写日志。Bridge 根据数量返回 [thrown](G:/VibeProj/spellcast/spellcast-bridge/src/lib.rs:268)。所以 `thrown` 甚至可能先于窗口创建成功。

解决方案：把请求接受、窗口创建成功、页面就绪分开记录；创建或调度失败要回到调用结果或可查询的投递状态。自主投递仍可立即返回“已接受”，之后由桌面发送实际就绪回执，不要求主任务等待 UI。报告必须使用对应证据：服务就绪、宿主工具可调用、窗口已创建、用户实际看到，是不同层级。

验收：模拟窗口创建失败时不能得到表示显示成功的结果；实际窗口完成后才能标记页面就绪；用户真实点击产生对应事件。一次真实看到也不能证明之后所有窗口都可靠。

**7. 记忆已有存储能力，但“用户可控”与“以后派上用场”还没完整落地。优先级 P1。**

长期记忆不是空话：[remember/recall/forget](G:/VibeProj/spellcast/spellcast-bridge/src/lib.rs:486) 和 SQLite/FTS 存储已存在，收藏也没有自动调用记忆写入。但“只有明确授权才写”主要由工具描述和 Skill 要求；当前 `remember` 参数是标题和文字，后端无法独立判断用户是否授权。应准确描述这个信任边界，不能说服务端已验证了用户意图。

还有一个当前可确认的行为漂移：仓库 [Skill](G:/VibeProj/spellcast/skills/spellcast/SKILL.md:34) 已写入记忆规则，本机安装的 [Codex Skill](C:/Users/Administrator/.codex/skills/spellcast/SKILL.md:34) 仍停留在旧版，只让 Agent 描述板状态。仓库更新不等于客户端实际生效。

解决方案：先提供最小的记忆查看、删除和来源展示，让用户知道保存了什么；候选与已确认记忆区分。用户在主对话明确要求记住时沿已有授权执行，不再为每条记忆额外弹确认；对于 Agent 自主提出的候选，再由用户选择保存。下一次相关任务按主题或来源召回，先沿用当前文字检索，拿不到实际漏检证据前无需换向量方案。

Skill 更新增加源版本或内容摘要与安装副本的对比；更新沿用当前备份安装器，不覆盖未知的用户修改。界面区分“已安装”与“宿主重载后已验证生效”。还应检查 MCP 内置指令与 Skill 的语义是否一致，避免两份规则分别演化。

验收：明确保存后能查看、召回、删除；仅收藏不会成为长期记忆；新任务可以找到相关内容；安装副本过期可被发现。自动召回只是上下文候选，不能把旧偏好强行当成当前命令。

**8. 之前的完成标准偏工程检查，开发顺序没有对齐产品风险。优先级 P1。**

先前模型报告了 Rust 测试、前端构建、Inspector 工具发现和配置修复，这些都是有效的工程证据。它也明确承认了客户端矩阵、反馈行为评测的缺口，这部分判断是好的。但是“功能完整”的措辞过满，随后优先建议记忆管理、签名、更新，而自然使用、并行成本和反馈接手尚未得到证明。

解决方案：工程检查继续做；产品验收加一层真实任务试用。交付顺序以核心承诺的风险为准，不以容易完成的功能清单为准。签名和发布对发行必要，但不能用来替代“用户为什么要一直开着 Spellcast”的验证。

**建议的实际实施顺序**

| 批次 | 具体交付 | 通过后能说明什么 |
| --- | --- | --- |
| 第一批：Codex 有限试验 | 验证本任务和子任务的原生工具权限；固定一次来源标识；Observer 在主任务继续执行时产生或放弃候选；补真实投递状态；读回一次用户反馈 | 一条真实旁念链路可以运行，主任务无需等待 |
| 第二批：让反馈与打扰可控 | 来源路由、未处理回复持久化与确认、统一投递控制、用户暂停、跨任务重试；复用 SQLite 与现有 UI | 多任务、重启、延迟回复时仍能正确处理 |
| 第三批：验证持续价值 | 修正 Skill 分发漂移；最小记忆管理；在数次真实创作中比较开启前后任务耗时、旁念质量和打扰感 | 决定哪些场景值得默认启用，以及下一宿主是否值得接入 |

第一批中的来源标识可以先是很薄的一层，但一旦允许多个真实任务接入，就必须先具备第二批的路由和恢复能力。不要为了第一批就自建常驻模型宿主、消息队列或通用自动化平台。

一条合适的最小旅程是：用户继续完成创作任务 → 宿主在明确节点给 Observer 简短材料 → 无价值就结束，有价值则投递候选 → 桌面按当前注意力策略显示 → 用户忽略则不追问，收藏则留板，回复则形成持久待处理项 → 原任务或获授权的后续处理者接手 → 只有改变主任务的部分进入主对话。阻塞问题始终走主任务沟通。
