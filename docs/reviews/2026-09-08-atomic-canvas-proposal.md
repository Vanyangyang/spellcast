用户已确认的产品目标：加速创意工作；提供各种原子表达，由 Agent 自由组合选择呈现。用户正在质疑卡片作为容器的必要性，不能把“卡片是基础容器”写成已确认约束。

建议先区分三个概念：

- 表达对象：可被呈现、定位和操作的内容。粒度可以是一段文字、一张图片、一幅 SVG、一张图表、一个 3D 视图，或带自定义交互的完整作品。原子不必细到每个像素、SVG path 或模型顶点。
- 组合：表达对象之间的组织关系，包括排列、叠放、嵌套、标注、连接和共享参数。分组本身不必画出边框或提供独立滚动区。
- 卡片：一种可选的视觉样式，可用于摘要、候选方案或需要明确边界的小组件。对象的布局包围盒、所有权和保存边界都不应强制显示成卡片。

当前倾向是“开放表达对象 + 无强制外框的组合”，同时保留完整 Web 作品作为可组合对象。Agent 为内容选择版式和交互；用户可以直接介入修改。不能简单地把当前卡片改成几个固定形状的白板工具，也不能要求所有讨论都先生成一个复杂网页。

| 候选组织方式 | 能解决的问题 | 主要代价 |
| --- | --- | --- |
| 所有内容进入卡片 | 边界和独立运行清楚，便于复用当前实现 | 嵌套视口、固定外壳和逐卡进入操作会继续限制编排 |
| 表达对象自由组合 | 内容可以具有主次，批注、版本和关系围绕对象发生 | 需要统一选择、编辑、组合和反馈锚点 |
| 整个工作面由一个 Web 作品生成 | 单次表达的布局和交互自由度高 | 局部更新、跨任务组合、用户改动合并和运行失败边界更难处理 |

建议的最小契约：

1. 每个可操作对象具有稳定 ID，并能追溯到来源任务、回复/块和内容版本。一个回复可以呈现多个对象；来源记录不会自动变成屏幕上的边框。
2. 对象具有明确的布局边界、选择行为、可编辑行为和生命周期。展示、编辑、导航的输入优先级一致；按住空格/中键仍可平移，输入控件不触发全局快捷键。
3. 优先原位操作；深入查看是按需能力。复杂作品仍可进入专注视图，原有阅读器不必成为所有对象的必经入口。
4. Agent 可以组合、变形、替换或展开现有对象，保留稳定引用和用户已修改部分。关系需要显式含义，不能只靠两个对象放得近来暗示因果。
5. 用户反馈附着到具体对象/区域及其确切版本。跨对象选择可以携带多个锚点；用户的选择与 Agent 的建议分别保留。
6. 宿主原生对象使用受控结构；自定义可执行作品继续隔离运行。跨对象的数据与动作通过声明的接口传递，不能以自由组合为由开放任意宿主 DOM 或控制接口。
7. 类型能力可扩展。第三方应用没有暴露内部对象时，它仍是整体操作对象；不自动承诺拆分任意 DOM，也不把栅格图片当作已有独立图层。
8. 使用最能推进当前工作的表达复杂度。一组命名候选可以只是清楚的文字；空间关系和动态机制才按需采用模型或交互实验。

现有实现可复用的部分：稳定 source/reply/block 身份、版本与状态保存、原任务反馈与确认、作品资源与运行隔离、草稿保留。当前 `src/canvas.ts` 以一条回复/想法对应一个 frame，并把正文操作移入阅读器；`spellcast-core/src/canvas.rs` 保存该层级的位置。这是需要重新划分的呈现层边界，不能靠删除 CSS 边框解决。

迁移候选：保留旧数据的原样读取和恢复能力，先让新表达对象引用现有块，允许同一回复自由编排多个对象。用一条真实创意工作验证新增组合与反馈契约，再决定哪些能力需要独立模型。此处尚不预定新库或大规模替换渲染引擎。

能证伪方案的三个场景：

- 命名或剧情头脑风暴：Agent 展开有区别的方向，用户选择、合并、要求反转，下一轮更新相关分支；无需用户逐条搬运卡片或整理一张复杂网页。
- 视觉创意：主图、局部选区、候选修改与批注同处一个工作面；“这里改成泳池”后可立即比较变化，保留其他选区和用户修改。
- 机制或空间探索：说明文字、参数、图表/模型与一个简短实验共同呈现；用户改变参数时相关内容一致更新，并能把当前状态交回原 Agent。

正式收敛前，Cursor 应独立质疑：原子粒度是否仍被现有 ReplyBlock 牵制；组合是否需要第一等数据结构；哪些交互应原生、哪些留在隔离作品内部；最小迁移是否真的降低创意推进成本。最终结论须区分用户已确认约束、主代理判断、Cursor 意见和未验证假设。

- `spellcast-core/src/canvas.rs:59` 的 `CanvasLayout::sync` 只接受 node/reply 身份；第 28–29 行将尺寸下限设为 280×200，不能直接承载小标签或独立线条。
- `src/reply-types.ts:58` 当前块类型为 text/comparison/graph/sequence/artifact。第 85 行的 `BoardReply` 同时持有来源和块集合；这可以继续作为传输与来源记录，但不必决定可见分组。

### 建议收敛的含义

| 概念 | 最少职责 | 不应隐含的限制 |
| --- | --- | --- |
| 内容对象 | 稳定身份、可呈现内容、内容版本、来源引用 | 一个对象必须是一条回复或一个现有 ReplyBlock |
| 画布实例 | 引用内容对象，保存位置、尺寸、层次和可选样式 | 同一内容的另一处展示必然是独立副本 |
| 组合 | 有身份的成员集合；允许整体操作、解组和可选布局关系 | 必须可见边框、标题栏或内部滚动区域 |
| 反馈锚点 | 对象与确切版本，按对象能力附带区域/子项/参数快照 | 屏幕坐标就是稳定语义引用，或任意图片已具备图层 |

这些是职责划分，不要求首版新增四套存储系统。先复用现有持久化与内容引用；只有真实需求需要同一内容多处呈现时，才实现额外实例。组合的成员身份不能只保存在 DOM，否则刷新后无法可靠追踪和更新。

原子粒度以“用户能独立选择、引用或修改什么”为准。短文字、图片、线条、图形和完整交互作品都可以是原子；对比、分支或流程可以由它们组合，也可以保留为整体对象。Agent 不必为一个标题生成网页，也不必把完整实验拆成几十个宿主控件。

首条验证链：Agent 呈现三个创意方向 → 用户把一个标题改掉、圈选某图局部并选择两个方向要求融合 → Agent 返回只涉及这些目标的修改 → 用户改过的标题、未选对象和已有排布保持可追溯 → 刷新后对象、组合与反馈仍正确。版本冲突须保留待应用修改并提示重新对齐；不默默覆盖用户改动。

最小迁移先让受支持内容在画布原位操作，并让一条回复能产出多个独立对象；旧回复仍可整体显示和恢复。下一步以这条验证链补齐组合与多锚点反馈，再按实际表达需要扩展类型。跨作品共享参数先通过明确动作与状态传递验证，不在首版引入通用响应式计算引擎。删除一个画布呈现与删除底层内容的语义必须分开说明，不能沿用当前删除整条回复的行为而不告知用户。
