# Canvas 是否需要独立组装模型

## 结论

当前暂缓新增独立 API 模型。先补齐原子组件的统一操作、idea 的组合语义、确定性编辑工具与原任务接续，再验证已有宿主 Agent 能否可靠完成组装。专用的组装职责可以建立，不必立即增加一个模型调用或新的模型服务。

这是用户要求与 Cursor Fable 5.1 讨论后，主代理复核代码得到的当前建议，并非已经接入模型或完成工作台验收。

## 实际讨论

- Cursor task：`cursor-mu0u41kt-7`，只读，正常完成并取回完整回复。
- `modelSelection.applied=true`；实际 `Claude Fable 5.1 High`，effort `high`。
- [Fable 原始意见](../../artifacts/workbench-20260914/cursor-mu0u41kt-7-review.md)。
- Grok executor 保持 OFF；没有新增 API 模型配置或调用。

## 主代理与 Fable 一致的判断

- 现有 Agent 已能调用 Canvas 批量操作。原子粒度、编辑交互、组合语义和任务生命周期缺口都需要工程实现，新增模型不会自动补齐。
- 自由拖动、缩放、选取、直接编辑、明确的组合/解组应走确定性操作。
- 对自然语言的组装请求，先由现有宿主 Agent 产出受约束操作，继续通过统一事务、版本检查、来源权限和冲突保护执行。
- 当前 source_id 同时影响写入所有权与反馈路由。新增写入者需要明确授权及来源记录，不能让模型自报成原任务，也不能把模型改动直接伪装成用户手工编辑。
- 当前没有对组装生成失败率、往返延迟或费用做公平测量；不能把独立 API 必然更快、更便宜当成事实。

## 对 Fable 意见的限定

- 独立模型并非技术上不可行。若只编辑当前 idea 的内容，且已明确授权、所需上下文完整，它可以提供价值；需要额外的执行与来源机制。
- 同宿主子代理不自动继承完整历史、写入身份或工具能力。未来如采用，先限定为生成组装方案，由原任务验证、提交；不把现有只读 Observer 直接改成写入者。
- Composition.members 本身是列表；当前缺的是明确的阅读顺序、内部布局行为和 idea 语义，而不是数据里完全没有成员顺序。
- 本机生成的 Codex 协议包含 thread/queue/start；但当前 Windows 的独立 stdio helper 尚未证明能安全控制桌面宿主的原任务。接口存在不等于原任务接续已打通。

## 什么时候再考虑专用角色或独立模型

1. 补齐组件协议后，已有 Agent 在真实组装样本中仍反复生成非法操作；分别统计 Invalid、正常版本冲突、用户保护和投递失败，不混为模型失败。
2. 用户明确需要原宿主未运行时，仍能在 Canvas 做自然语言局部修改。
3. 在相同输入、组件能力和验收要求下，替代路径确实改善响应时间、修改成功率或费用。
4. 跨来源授权、修改记录、撤销和原任务重新接手已经定义并验证。

## 最小下一步

用已有宿主 Agent 组装“说明文字＋对比＋关系图＋可调作品”这个同一 idea，核对首次操作、局部回改、整体移动、重启恢复和真实反馈回填。记录失败在哪一层，再决定是否需要新增模型。
