## 哪些建议需要修正后采用

### 1. 路线到达与体验有效分别记录

Claude 提议显示钩子的“线索、动作、回报”兑现情况。我只支持把可以确定的事实自动化，例如“到达线索步骤”“选择已执行”“回报步骤未到达”。

玩家是否注意到线索、是否理解动作、回报是否足以推动继续，需要评审或真实观察。**不能因为流程走通，就自动显示“钩子兑现”或“体验通过”。**

### 2. 步骤是体验的定位点，共用对象仍可独立存在

对一次体验，步骤和选择适合连接相关设计。但 Claude 所说“唯一汇合点”“素材需求只能由时刻和钩子阶段派生”过于严格。共用规则、全局参数、统一画风、通用 UI 和可复用素材可以独立存在，再引用到多个使用位置。

优先扩展现有步骤/选择的引用能力即可，不必新增一个让用户理解和维护的“玩家时刻”对象类型。引用放在哪一侧需要结合锁定语义决定；挂接内容不应无故要求解锁稳定骨架。

原文所说“跨对象的类型化连接只有变量到数值”应限定为流程执行模型。整个规划模型已经有归属、使用、依赖和先后关系；缺的是这些设计关系与具体步骤、选择的衔接。

### 3. 重放不能悄悄复用外部结果

同一输入和选择意图适合用来比较方案，遇到分歧应明确停止并解释。对于战斗等手动或外部步骤，应暂停索取结果，或由用户明确选择复用为“本次假设”。

如果候选改变了这些外部过程的输入，旧结果不能自动成为新方案的验证证据。

### 4. 技术验证与真实内容验证可以分步完成

Claude 指出了示例不能保存、真实 R0 内容尚未提供的问题。技术上的保存、锁定、导出和引用完整性可以用隔离测试数据验证；产品是否适合实际设计，则需要用户确认的一小段新 R0 内容。

这不要求先提供完整游戏设计，也不允许把演示或旧配置写入真实项目。

## 调整后的最小工作顺序

1. **步骤与设计关联**：在现有流程上定位对应内容、规则和钩子，双向跳转；引用失效时能看见问题。
2. **候选与试走保存**：候选记录基准，完整试走可被稳定引用，重开和导出/导入后仍能找到。
3. **比较与采用**：同样的输入和选择意图下比较两套明确建模的方案，解释分歧；采用时保留理由、差异和运行记录，并遵守现有锁定及版本检查。
4. **制作需求与素材**：从具体使用位置建立需求，接入占位素材和候选；之后再按真实需求接生成、切片、检查等工具。

这个顺序保留原 Canvas 入口和自由组合能力，也保留“系统骨架 + 内容叠加”。Scenario、CastleDB、LDtk、inkjs 等调研仍然有价值，接入顺序由需要完成的操作决定。

## 附录：Claude 原评审全文

以下保留原评审中的判断与表述；其中的建议应结合上面的主任务复核理解。

我的判断：方向对，但顺序和落点需要调整。报告对 Scenario 的提炼很准，第三节列出的四条代码事实我逐条核对过，都属实。问题在于第一段放在了素材上，而现在最缺的连接在"玩家时刻"上（玩家处在流程的哪一步、做哪个选择）。

### 1. 最有价值的两点，不同意的两点

**最有价值**

- **三类证据分开**：程序检查、评审意见、游戏内证据各自标明对象和版本，不共用一个"完成"状态；报告也明确美术评分不能证明好玩或数值平衡。这条应该成为整个工作台的规则。
- **引用不等于备份**：导出时外部文件标为 `original_included=false`（`project_record_store.rs:2158-2198`）。区分"仅链接 / 本地副本 / 打包带走"，补的是持久化的真实缺口。

**不同意或证据不足**

- **第一段没有真实落点。** R0–R2 还没有确认过的内容，验收允许用"明确标记的示例"。但按现有契约，示例只存在内存里、不能保存（`game-planning-workspace-contract.md:45-47`），所以你最看重的持久化、锁定、历史没法在真实数据上验证。`content` 又是结构最少的类型，`emptyPlanning` 不给它任何专门字段（`project-planning-model.ts:26-33`）。把最复杂的面板挂在最空的对象上，正是它变成资产收纳器的起点。验收里的"能找到所属系统和钩子"只检查导航，不检查素材是否服务于那个钩子。
- **漏掉了更大的断点，也低估了方案对照的工作量。** 报告的叠加图暗示"流程 → 内容 → 钩子/规则"是连着的，但代码里流程步骤不引用任何对象，只有文字和选择（`game-flow-model.ts:8`、`project_flow.rs:27-36`）。跨对象的类型化连接只有"流程变量 → 数值对象"一条（`project_planning.rs:241-249`）。报告把方案对照写成"沿用现有能力、并行推进"，实际上试走既不能选候选，也不能重放，记录还只存在本地（见第 5 点）。

### 2. 最该先补的流程：在一条 R0 流程上验证钩子能否兑现，同一路线比较两套数值，再采用其中一套

用户的实际操作是这样的：

1. 打开自己的 R0 流程，把钩子"首次探索值得继续"的线索、动作、回报分别标到步骤 1、选择 1a、步骤 3。流程本身保持锁定。
2. 试走时，每一步旁边显示在这里出现的钩子阶段和相关规则原文。走完得到"线索✓ 动作✓ 回报✓"，或者"回报未到达"。
3. 给"体力"选候选 B，按同一串选择重放，看到第一处分歧（例如步骤 1 因为体力 1 < 2 被阻断）和最终数值差异。
4. 采用 A，写明理由并引用这两次试走，然后保存并锁定。

为什么它比其他候选更优先：

- 这是"骨架 + 叠加"真正闭合的地方：体验、规则、数值、流程在同一次可重复的检查里被串起来。
- 只用用户自己的数据，不依赖素材、账号或旧配置。
- 素材需求和 Unity 证据都需要"哪个玩家时刻"作为落点，否则只会挂在对象上越积越多。
- 表格化数值编辑要等参数多起来才划算，叙事运行时要等真正出现对话需求。

### 3. Scenario：迁移什么，不搬什么

**值得迁移**

- 候选不改动已采用的基准；"采用"是唯一改写基准的操作。
- 先写可观察的标准，再动手制作，并限制迭代次数。钩子的线索和回报本身就可以当标准。
- 执行前冻结输入和版本。`FlowRun` 快照已经做到，只需补上"这次用了哪个候选"。
- 文件身份清单（角色、哈希、版本）。等出现真实文件时再并入 `SourceReference`。

**不适合原样搬入**：默认走付费 MCP 生成；把 Quality Gate 分数当作通过；把 seed 当作一致性保证；承诺能导入外部工作流图；以素材库为中心的数据结构。独立的 Identity Library 搬过来会成为第二份需要维护的数据。

**怎样关联才不分裂（设计建议）**：以流程里的某一步或某个选择作为唯一汇合点。

- 钩子、规则、内容在各自对象上声明锚点（步骤或选择 ID + 阶段），不写进流程骨架。这样挂接钩子时不用解锁流程。
- 规则原文和选择上的类型化条件通过锚点对照，缺了哪一边就给出诊断。
- 素材需求只能从"时刻 + 钩子阶段"派生，并继承验收标准，例如"步骤 3 里玩家能认出可交互物"。没有使用时刻的需求直接标出来。
- 三类证据都指向同一个时刻和版本。

### 4. 建议先做的最小一段

**范围**：钩子和规则锚定到步骤与选择；试走显示锚点和兑现摘要；数值候选与已采用的数值分开保存，可以选候选按原来的选择顺序重放；采用时关联试走；试走记录存进项目数据。

**可检查的验收动作**（用隔离的测试数据）：

1. 在锁定的流程上挂接钩子的三个阶段，流程版本号不变。
2. 删除被锚定的步骤时，保存被拒绝，或者锚点显示为悬空，不会悄悄消失。
3. 两条不同路线分别得到"兑现✓"和"回报未到达"。
4. 新增候选 B 后，基于 A 的试走不会失效；重放 B 时标出第一处分歧；手动步骤沿用记录的值，并标为"手动假设"。
5. 采用 A 后，历史里多一个版本，记下候选名、理由和两次试走的 ID；带局部值的使用方不受影响。
6. 重启、导出再导入后，锚点、试走和采用依据都完整保留；演示数据一条都没写入。

**暂缓**：素材候选比较面板、生成服务和 ComfyUI 提交、精灵和等距模板、glTF 检查、inkjs、LDtk、概率与经济模拟、表格化数值编辑。第二段再做"由时刻派生的制作需求清单 + 占位素材引用"。

### 5. 结构性风险（先写读到的代码事实，"→"后面是设计建议）

- **候选存在已采用的对象里面。** `ParameterDefinition.variants` 没有记录"采用了哪个"，采用只是把值复制过去（`project_planning.rs:78-102`、`project-planning-view.ts:361`）。所以新增一个候选必须先解锁已采用的数值。而判断试走是否过期是比较整个对象的 JSON（`game-flow-model.ts:154-156`），连解锁、加锁都会让已有试走过期，A/B 对照没有稳定的基线。→ 候选单独保存，引用基准的 ID 和版本；过期判断只比较真正影响计算的值。
- **试走证据不持久。** 试走存在浏览器本地存储里，每个流程只有当前和上一次两份，每开一次新试走就覆盖更早的那份（`game-flow-workspace.ts:35,61,87-92`），导出包里也没有（`project-record-api.ts:76-85`）。但开发记录摘要被截断时写着"完整轨迹保留在本地试走记录中"（`game-flow-model.ts:162`），再试走两次，这句话就不成立了。
- **规则有两套互不相连的表达。** 规则对象是自由文字（`project_planning.rs:54-61`），流程选择上的条件是类型化的，两者没有关联；影响分析 `planningImpact` 只沿着对象间的关联追踪（`project-planning-model.ts:35-48`），改了规则看不到哪些选择受影响。另外，现有校验禁止同一对象对同一目标重复同一种关联（`project_planning.rs:257`）。→ 钩子三个阶段的锚点应放进钩子定义里，或放进一条关联的锚点列表，而不是建三条关联。
- **变成收纳器的具体路径。** 如果把素材做成新的规划类型叠加到图上，每个节点只展开 5 项（`project-planning-map.ts:131`），系统图很快会被素材挤满。→ 素材先只以数量的形式显示在内容和时刻上。

**一句话结论**：我不支持目前的优先顺序。应该先做"流程时刻锚定 + 钩子兑现试走 + 同一路线的数值候选对照与采用（候选单独保存、试走持久保存）"，再做"由时刻派生的制作需求与占位素材"；素材候选比较、采用和生成工具接入，放到有已确认的 R0 内容之后。
